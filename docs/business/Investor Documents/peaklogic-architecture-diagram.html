Reading the diagram

A fixed vocabulary of shapes, used consistently, plus a lettered badge on every boundary — cross-referenced below — so a review conversation can say "look at E" instead of re-pointing at the screen. One honest limitation: these are hand-drawn analogues of the well-known Azure shapes, not Microsoft's own licensed icon set, which this document's build process has no way to embed.

Boundaries

On-prem boundary — the customer's own network. Nothing inside requires an inbound rule from the cloud.
Azure tenant boundary — every managed service PeakLogic operates.

Tenant isolation

Every tenant-scoped query runs inside a transaction that sets app.current_tenant_id via set_config(), activating PostgreSQL RLS — forced, not merely enabled, and with no BYPASSRLS role. A site outside a viewer's scope is refused, never approximated.

Deployment reality

Defined in Bicep, validated by az bicep build and PSRule on every push. No environment deployed yet — this diagram describes the architecture as designed and CI-validated, not a running production system.

Cost containment

Dev and staging each carry a dedicated Cost Kill-Switch Function (its own least-privileged identity, scoped only to that stage's Postgres resource) that stops the database at 100% of budget. Prod deliberately does not carry this function — an automated stop is an availability risk that environment doesn't accept — and instead gets a real four-threshold budget routed entirely to email. Agents run on the existing consumption plan — additive spend is near $0.

Cloud governance & subscription topology

How the Azure tenant itself is organised

What this diagram shows — the deployment path: how code in source control becomes running Azure infrastructure, and what separates dev from production. Top to bottom: (K) the GitHub repository (CI on every push, one deploy workflow per stage) → Entra Workload Identity Federation, issuing each stage its own App Registration that trusts this repo over OIDC, so no client secret is ever stored → three resource groups, one per stage, each with a full copy of the platform's services and its own budget guardrail → (L) the two-step mechanism every deploy performs. The coloured dot above each resource group is its trigger: dev deploys automatically; staging and prod need a human to start the run. Dev and staging carry an automated Cost Kill-Switch Function that can stop their own database at 100% of budget; prod deliberately does not — see the card below. Pages 1–3 cover how data moves through the running system; this page covers how that system gets deployed.

Operational behavior · growth, failure, change, daily operation

How the system behaves, not just what protects it

Pages 1–4 answer "what protects the system" — isolation, authentication, encryption — in real depth. They don't answer four other questions an operator or investor should ask: does it scale on real numbers or hope, does it come back from a failure, can it change safely, and would anyone know if it were unhealthy right now. Four quadrants, each sourced from a real file or CI job, each paired with its honest gap rather than a rounded-off claim.

Scale — numeric triggers, not guesses

SitesTriggerAction
~250Postgres Burstable tier saturatesMove off Burstable — the platform's own "first real decision" point
~2,000Full-scan cost on the telemetry table hurtsPartition by month — already a comment in the live schema
~2,778IoT Hub S1 capacity reachedMove to S2; evaluate direct Event Hub consumption for the largest sites

No new infrastructure is justified before these are hit — not Kafka, not Cosmos DB, not a dedicated broker, not a physical microservice split.

Recover — real mechanisms, one open gap

✅Postgres backups: 7-day retention every stage; prod adds geo-redundant backup + zone-redundant HA
✅Ingest never silently drops a message — a poison-message table captures what a retry can't fix, and a duplicate reading is a no-op, not a double-count
✅A scheduled sweep across every tenant isolates one tenant's failure — it never aborts the run for everyone else
✅A cost-triggered database stop (dev/staging only) auto-restarts within 7 days regardless of cause — an Azure platform guarantee, not custom code
🟡Tenant-scoped restore is a documented 5-step manual runbook (restore to scratch → isolate → extract → review → replay) — not an automated capability. Point-in-time restore itself is whole-instance only
🔴RPO ≤5min / RTO ≤4hr are real, defined targets — never drilled against an actual restore

Evolve — safe rollout, two open gaps

✅SemVer + Conventional Commits — every schema/API/security change is classified MAJOR/MINOR/PATCH before it ships, not after
✅New capabilities ship behind an off-by-default flag — disabling one is a flip, not a redeploy
✅CI proves the full migration set applies cleanly before merge; dev deploys on push, staging/prod require a human to start the run
🟡Rollback is a documented tag-and-redeploy procedure — written down, never yet exercised as a drill
🔴Firmware/software release channels exist as a label on the Hub model only — no eligibility rules, staged rollout, or health-gated rollback yet
🔴Over-the-air update delivery is 0% built — signing, staging, install and rollback are design-only

Operate — what's actually watching it

✅Every request carries a correlation ID end to end, echoed in logs and the audit trail
✅5 metric alerts (Postgres CPU/storage/failed-connections, IoT ingest-rate-zero, API 5xx) auto-resolve when the metric recovers, not just when someone closes them
✅A dedicated agent proves tenant isolation holds on every CI push — the one continuously-running proof in a system whose isolation mechanism has failed silently once before
✅Every state-changing action, including platform-level ones like a kill-switch trip, writes to an immutable audit log
🟡The 16-agent operations team: 2 agents live, 10 assembled from existing subsystems, 4 still design-only — tracked honestly per-agent, not claimed as one finished "AI ops team"
🔴No SLO/SLI definitions or dashboards exist yet, despite the telemetry to build them already being collected
