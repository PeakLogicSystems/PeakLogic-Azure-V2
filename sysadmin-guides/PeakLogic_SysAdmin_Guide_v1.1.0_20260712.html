1. System Overview

PeakLogic is a multi-tenant, cloud-native IoT SaaS platform that monitors industrial and commercial equipment — pumping stations, HVAC systems, pool equipment, and QSR (quick-service restaurant) assets — in real time. Sensors attached to physical equipment transmit telemetry data to AWS IoT Core over MQTT/TLS. The platform evaluates that data against threshold rules, raises alerts, and automatically creates service tickets for partner companies when critical thresholds are breached.

As of v1.1.0, the platform also supports a second, separate user population: channel partners — pool-service companies (e.g. a Pinch-A-Penny franchise) who install PeakLogic sensors at their own customers' sites and log into a white-label, branded portal to draw technician territories, dispatch daily routes, and see real-time chemistry/status data across every customer site attributed to them. This is a genuinely separate identity and access surface from the tenant-side application described throughout most of this guide — see §5.5 and §8.2.

Business Purpose

  • Detect abnormal equipment behavior before failure occurs
  • Reduce risk of equipment damage and property loss for customers
  • Proactively trigger service tickets to partner service companies via webhook
  • Give channel partners real, continuously-measured evidence (chemistry, status) to justify service visits, replacing manual field checks

Multi-Tenancy Model

PeakLogic uses a hybrid pooled model: all tenants share a single PostgreSQL database, but every tenant-scoped table carries a tenant_id column and PostgreSQL Row-Level Security (RLS) policies enforce data isolation at the database level. No application query can accidentally cross tenant boundaries because the database engine enforces it.

v1.1.0 — RLS is now actually enforced against the app's own DB role
Prior to v1.1.0, the application connected to PostgreSQL as peaklogic_admin — the same role that owns every table. PostgreSQL table owners silently bypass RLS by default unless FORCE ROW LEVEL SECURITY is explicitly set, which no table in this schema ever had. This meant every "RLS enforces isolation" claim in this platform's history, back to the very first migration, described a mechanism that would not have actually worked once deployed. It was never live-exploited (nothing had been deployed to a real AWS account before this was found), but it is the single most important fact in this release. See §6.3 for full detail.

Channel-partner access is a second, deliberately different scoping dimension layered on top of the tenant model above: a channel-partner session can read across every tenant attributed to it (via tenants.channel_partner_id), and a technician's session is further restricted to the sites within their own assigned territory. This is enforced the same way tenant isolation is — real PostgreSQL RLS policies, not application-level filtering — see §6.3.

2. Architecture & Infrastructure

All infrastructure is defined as code in the infra/ directory using AWS CDK v2. Eight CDK stacks are deployed in order (grew from 6 at v1.0.0 — Monitoring and CI/CD were added in v1.1.0). Each stack's outputs are consumed by subsequent stacks.

Every stack name is stage-suffixed — there is no default stage
As of v1.1.0, every CDK command requires an explicit -c stage=dev|staging|prod context value. A missing flag fails the command outright rather than silently deploying somewhere unintended. Stack names below use PeakLogic-{stage}-*, e.g. PeakLogic-dev-Api. See §4.

One deliberate exception to stage isolation
The MQTT topic namespace itself (peaklogic/{thingName}/telemetry) is not stage-scoped — only the IoT Core resource names above are. Staging the topic namespace too would mean touching device firmware/provisioning config. Consequence: if dev and prod IoT stacks are ever both deployed to the same AWS account, both stages' ingest Lambdas would fire on the same device's telemetry. Operational rule: only one stage's IoT stack may be deployed per AWS account at a time, unless using genuinely separate AWS accounts per stage.

4. Initial Deployment Procedure

This platform has never been deployed to a real AWS environment
As of v1.1.0, no AWS account has ever been used with this project (confirmed directly with engineering leadership). Everything below is a reviewed, typechecked, tested-in-isolation procedure — not a proven runbook. Follow it carefully and expect to debug real first-deploy issues that can't be caught without a real account: a few are already known in advance and listed inline below.
Prerequisites
  • AWS CLI installed and configured (aws configure) with an IAM user/role that has Administrator-level permissions
  • Node.js 20 LTS installed
  • Git installed and authenticated with GitHub
  • AWS account bootstrapped for CDK (one-time per account/region)

Step 1 — Clone the repository

git clone https://github.com/PeakLogicSystems/PeakLogicSystems.git
cd PeakLogicSystems
git checkout main   # or dev for the latest unreleased work

Step 2 — Bootstrap CDK (first time only)

This creates an S3 bucket and IAM roles that CDK needs to deploy stacks. Run once per AWS account per region.

Known risk — GitHub OIDC provider collision
If a GitHub Actions OIDC provider for token.actions.githubusercontent.com already exists in the target AWS account for an unrelated reason, the CI/CD Stack (§2.8) will fail to deploy with a duplicate-resource error. This can't be verified without real AWS access — if it happens, either reuse the existing provider or remove the conflicting one before retrying.

5. User & Tenant Management

5.1 Creating a New Tenant

A tenant is a customer organization. Creating a tenant is a two-step process: insert the DB record, then create users in Cognito and link them via custom:tenant_id.

-- 1. Insert tenant record
INSERT INTO tenants (id, name, slug, plan, status, settings)
VALUES (
  gen_random_uuid(),
  'Customer Name',
  'customer-slug',   -- lowercase, no spaces, used in URLs
  'starter',         -- starter | professional | enterprise
  'active',
  '{"webhook_url": "https://partner.example.com/webhooks/peaklogic"}'
)
RETURNING id;  -- save this UUID

-- 2. Verify it was created
SELECT id, name, slug, plan, status FROM tenants WHERE slug = 'customer-slug';

After creating the DB record, create at least one admin user in Cognito (see §5.2) with that tenant's UUID as their custom:tenant_id.

5.2 Creating User Accounts

All user creation goes through the AWS Cognito console or CLI. Self-registration is disabled.

Via AWS Console

  1. AWS Console → Cognito → User Pools → peaklogic-{stage}-users (the tenant pool — for a channel-partner user, see §5.6 instead)
  2. Users tab → Create user
  3. Set Invitation message to send temporary password by email
  4. Enter the user's email address
  5. Under User attributes, click Add attribute: custom:tenant_id → the tenant UUID from the DB
  6. Click Create user
  7. In the Users list, click the new user → Add user to group → admin or operator (§5.3) — this step is what actually grants access, not the attribute above

Via AWS CLI

aws cognito-idp admin-create-user \
  --user-pool-id YOUR_USER_POOL_ID \

6.3 Row-Level Security (RLS) — including the FORCE RLS fix

Read this box before touching RLS on this platform
The v1.0.0 version of this guide said "as the peaklogic_admin superuser, RLS is bypassed automatically" — that framing was wrong, and describes exactly the bug this release fixed. peaklogic_admin is not a real PostgreSQL superuser (RDS never grants that on the master user) — it appeared to bypass RLS for a completely different reason: it owns every table (it's also the role every migration runs as), and PostgreSQL table owners silently bypass RLS by default, independent of superuser status, unless FORCE ROW LEVEL SECURITY is explicitly set on the table. No table in this schema had that set before v1.1.0. This means every "RLS enforces isolation" claim in this platform's history — including the very tenant isolation this section exists to document — described a mechanism that would not have actually held once deployed against a real database, since the app connects as this same table-owning role. It was never live-exploited (nothing had been deployed to a real AWS account when this was found), but it would have been on the very first real deploy. Fixed in migration 1783728060000_force-row-level-security.sql — every RLS-enabled table now also has FORCE ROW LEVEL SECURITY, and this guide's examples below reflect the corrected, actually-enforced behavior.

Every tenant-scoped table has RLS enabled and forced. The application sets the active tenant via a PostgreSQL session variable at the start of every transaction:

BEGIN;
SET LOCAL app.current_tenant_id = 'TENANT_UUID';
-- All queries in this transaction are automatically filtered to this tenant
SELECT * FROM sites;  -- returns only this tenant's sites
COMMIT;

To query data as a specific tenant in a psql session (for debugging) — this now genuinely enforces isolation, including for peaklogic_admin:

BEGIN;
SET LOCAL app.current_tenant_id = 'YOUR_TENANT_UUID';
SELECT * FROM devices WHERE status = 'online';
ROLLBACK;  -- or COMMIT if making changes

Channel-partner sessions use a different set of variables — added v1.1.0

A channel-partner request never sets app.current_tenant_id at all. Instead:

BEGIN;
SET LOCAL app.current_channel_partner_id = 'PARTNER_UUID';
SET LOCAL app.current_channel_partner_user_id = 'CHANNEL_PARTNER_USER_UUID';
SET LOCAL app.current_channel_partner_role = 'technician';  -- or 'partner_admin'
-- A partner_admin sees every route under their partner;
-- a technician sees only their own day's route.
SELECT * FROM route_assignments;
COMMIT;

Every pre-existing tenant_isolation policy uses current_setting(..., true) (the missing_ok form) rather than erroring when app.current_tenant_id is unset — a real, deliberate fix, since a channel-partner session never sets it, and the original policies would have thrown an error rather than simply denying access, before the new cross-tenant policies ever got evaluated.

Querying across all tenants for legitimate ops/reporting purposes

No dedicated reporting/bypass role exists yet
There is currently no non-owning, RLS-bypassing application role built for this platform (a real, flagged-but-not-implemented option — Multi-Tenant Architecture §6 item 6, tracked as TD-7 in the Technical Debt Register). AWS RDS also blocks granting the BYPASSRLS attribute outright. The only way to run a genuine cross-tenant query today is to temporarily disable forcing on the specific table, as peaklogic_admin (which owns every table and therefore has this privilege), then restore it immediately: 
-- Temporarily disable, run the cross-tenant query, then RE-ENABLE immediately.
-- Never leave a table in this state.
ALTER TABLE devices NO FORCE ROW LEVEL SECURITY;

SELECT t.name AS tenant, count(d.id) AS device_count
FROM tenants t
LEFT JOIN devices d ON d.tenant_id = t.id
GROUP BY t.name;

ALTER TABLE devices FORCE ROW LEVEL SECURITY;  -- do not skip this step

Treat this as a rare, deliberate, logged administrative action — not a routine query pattern. If cross-tenant reporting becomes a frequent need, that's a real argument for finally building the dedicated non-owning reporting role (TD-7).

Device-claim and provisioning sessions — added v1.1.0

A device before it's claimed by a customer has tenant_id = NULL. Reading/writing it (during claim, or during scripts/provision-devices.ts) requires its own dedicated session markers, since neither app.current_tenant_id nor a channel-partner marker applies:

-- Device claim flow sets:
SET LOCAL app.claim_context = 'true';
-- Provisioning script sets (plain SET, not SET LOCAL — the script isn't
-- wrapped in one single transaction for its whole run):
SET app.provisioning_context = 'true';

These are intentionally narrow — each only grants the one specific lookup it's needed for (an unclaimed device by serial), not general device visibility. An earlier draft of this fix briefly leaked every unclaimed device system-wide to any tenant's normal device list before being caught in review; the shipped version does not have this problem, but it's a useful example of how easy this class of bug is to introduce when adding a new RLS policy — always ask both "does this still work for every legitimate caller" and "could this grant more than intended to some other caller running the same query."

7.4 Revoking a Device Certificate

Use this when a device is decommissioned, lost, or its key is suspected compromised.

# 1. Find the certificate ARN (stored in device-config.json or IoT console)
CERT_ARN="arn:aws:iot:us-east-1:ACCOUNT:cert/CERT_ID"

# 2. Deactivate the certificate (blocks MQTT connections immediately)
aws iot update-certificate \
  --certificate-id CERT_ID \
  --new-status INACTIVE

# 3. Detach from thing
aws iot detach-thing-principal \
  --thing-name plg-0001 \
  --principal $CERT_ARN

# 4. Detach policy
aws iot detach-policy \
  --policy-name PeakLogicDevicePolicy \
  --target $CERT_ARN

# 5. Delete the certificate
aws iot delete-certificate --certificate-id CERT_ID

# 6. Mark device as decommissioned in DB
UPDATE devices SET status = 'decommissioned' WHERE thing_name = 'plg-0001';
Known gap — the app's own decommission endpoint only does Step 6
DELETE /v1/devices/{deviceId} (§8.1) only runs the DB status update in Step 6 above — it does not call IoT Core to deactivate/detach/delete the certificate. A "decommissioned" device, by the application's own database, still holds a live, active certificate that can reconnect and publish indefinitely unless Steps 1–5 above are also done manually, every time. This is a real, disclosed, unfixed gap (Device & Command Security Architecture §3.2), not an oversight in this guide — always perform this full 6-step procedure manually, not just the API call.
Also unaddressed — routine certificate rotation policy
The steps above cover one-off revocation (decommission, loss, compromise). A routine rotation policy for still-in-service devices — rotating a certificate periodically as a hygiene practice, independent of any specific incident — was explicitly deferred from Device & Command Security Architecture to Security Architecture, and Security Architecture never actually picked it up. No owner, no design exists yet (tracked as TD-9 in the Technical Debt Register, §16).

Rules moved out of backend/ingest/handler.ts into a new, pure, unit-tested module: backend/ingest/rules.ts (exports RULES_BY_CATEGORY, evaluateRules(), and sanitizeMetrics()). This was previously inline inside the DB-touching handler and untestable in isolation. handler.ts now calls into this module rather than defining rules itself.

Alert rules are evaluated in the ingest Lambda every time a telemetry payload arrives. Rules are hardcoded per asset category in backend/ingest/rules.ts. To modify thresholds you must edit the source code and redeploy the Lambda.

v1.1.0 — telemetry values are now validated before use
A new sanitizeMetrics() function drops any metric value that isn't a finite number (null, a non-numeric string, NaN, Infinity) before it reaches either the database INSERT or rule evaluation. Previously a malformed value could reach both unchecked — a real, disclosed gap (Threat Model §4.1) found while testing, not an externally reported issue. Dropped metrics are logged; the rest of the payload still gets processed normally.

Alert Deduplication

Before creating a new alert, the ingest handler checks whether an open or acknowledged alert already exists for the same device, metric, and severity. If one exists, the ingest completes silently without creating a duplicate. This prevents alert storms during sustained threshold violations.

Auto-Ticket for Critical Alerts

When a CRITICAL alert is created, the ingest handler automatically:

  1. Looks up the tenant's settings.webhook_url from the tenants table
  2. Creates a service ticket with priority = emergency linked to the alert
  3. POSTs the ticket payload to the webhook URL via backend/shared/webhook.ts's postWebhook() (fire-and-forget, 8-second timeout)
v1.1.0 — Critical SSRF fix, live and exploitable in v1.0.0
POST /v1/tickets previously accepted an arbitrary webhookUrl directly from the request body with zero validation — any authenticated operator+ user could make this Lambda send an outbound request anywhere they chose, including internal network reconnaissance. The same unguarded pattern existed a second time in this exact auto-webhook code path. Fixed with a shared, tested postWebhook() function: HTTPS-only, resolves the hostname, and rejects private/loopback/link-local address ranges (including 169.254.0.0/16, which covers EC2's IMDS, ECS/Fargate's task-metadata endpoint, and Lambda's own AZ-metadata endpoint). Disclosed residual gap: validates at check-time, not connection-time, so DNS rebinding isn't fully closed — tracked as TD-2 in the Technical Debt Register (§16), judged disproportionate to fully solve at MVP scale.

Authentication Flow

The frontend uses AWS Amplify v6 with the tenant Cognito User Pool (§2.3) configured in frontend/src/amplify-config.ts. Only the tenant side has a frontend — the Partner Pool has no corresponding UI yet. Authentication flow:

  1. User visits the app URL — Amplify Authenticator intercepts and shows the login form
  2. User enters email and password
  3. If first login, user is forced to set a new password
  4. Optionally, user sets up TOTP MFA (Google Authenticator)
  5. Cognito returns ID + Access tokens (stored in localStorage)
  6. App renders; tokens are refreshed automatically by Amplify before expiry
  7. Every API call injects the ID token as the Authorization header

13. Security Hardening

Network Security

  • RDS is in an isolated subnet with no internet gateway route — unreachable from the internet
  • Lambda can only reach RDS because the Lambda Security Group is explicitly allowed on port 5432 in the RDS Security Group
  • API Gateway is the only internet-facing entry point to the application
  • All traffic between CloudFront and S3 uses Origin Access Control — the S3 bucket URL is private

Authentication & Authorization

  • Cognito JWT tokens expire after 1 hour; refresh tokens expire after 30 days
  • All API routes require a valid JWT — there are no unauthenticated endpoints
  • Role-based access is checked in every route handler via requireRole()
  • Tenant isolation is enforced by PostgreSQL RLS — application code cannot bypass it
  • Self-registration is disabled — users can only be created by an administrator

Secrets Management

  • DB credentials are stored in AWS Secrets Manager — never in environment variables in plaintext
  • Device private keys are in device-certs/ which is gitignored — never committed to source control
  • .env and .env.local files are gitignored — never committed to source control
  • Added v1.1.0 DB credentials rotate automatically every 30 days, all stages
