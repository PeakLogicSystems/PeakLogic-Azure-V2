1. System Overview

PeakLogic is a multi-tenant, cloud-native IoT SaaS platform that monitors industrial and commercial equipment — pumping stations, HVAC systems, pool equipment, and QSR (quick-service restaurant) assets — in real time. Sensors attached to physical equipment transmit telemetry data to AWS IoT Core over MQTT/TLS. The platform evaluates that data against threshold rules, raises alerts, and automatically creates service tickets for partner companies when critical thresholds are breached.

Business Purpose

  • Detect abnormal equipment behavior before failure occurs
  • Reduce risk of equipment damage and property loss for customers
  • Proactively trigger service tickets to partner service companies via webhook

Target Verticals

VerticalAsset CategoriesKey Metrics
Pumping Stationspumppower_kw, flow_lpm, pressure_psi
QSR (Restaurants)hvac, compressortemp_c, power_kw
Pool Monitoringpool_systemflow_lpm, temp_c, ph

Multi-Tenancy Model

PeakLogic uses a hybrid pooled model: all tenants share a single PostgreSQL database, but every tenant-scoped table carries a tenant_id column and PostgreSQL Row-Level Security (RLS) policies enforce data isolation at the database level. No application query can accidentally cross tenant boundaries because the database engine enforces it.

2. Architecture & Infrastructure

All infrastructure is defined as code in the infra/ directory using AWS CDK v2. Six CDK stacks are deployed in order. Each stack's outputs are consumed by subsequent stacks.

infra/bin/peaklogic.ts  (CDK App entry point)
├── PeakLogic-Network   → VPC, subnets, security groups
├── PeakLogic-Data      → RDS PostgreSQL, Secrets Manager
├── PeakLogic-Auth      → Cognito User Pool + App Client
├── PeakLogic-Api       → Lambda functions + API Gateway
├── PeakLogic-IoT       → IoT Core: thing type, policy, rule
└── PeakLogic-Frontend  → S3 bucket + CloudFront distribution

4. Initial Deployment Procedure

Prerequisites
  • AWS CLI installed and configured (aws configure) with an IAM user/role that has Administrator-level permissions
  • Node.js 20 LTS installed
  • Git installed and authenticated with GitHub
  • AWS account bootstrapped for CDK (one-time per account/region)

Step 1 — Clone the repository

git clone https://github.com/PeakLogicSystems/PeakLogicSystems.git
cd PeakLogicSystems
git checkout dev

Step 2 — Bootstrap CDK (first time only)

This creates an S3 bucket and IAM roles that CDK needs to deploy stacks. Run once per AWS account per region.

cd infra
npm install
npx cdk bootstrap aws://YOUR_ACCOUNT_ID/us-east-1

Step 3 — Deploy all stacks

npx cdk deploy --all --require-approval never

This takes approximately 10–15 minutes. CloudFormation deploys all 6 stacks in dependency order. When complete, the terminal outputs key values you will need:

CDK Output KeyUsed For
PeakLogic-Api.ApiUrlFrontend VITE_API_URL
PeakLogic-Auth.UserPoolIdFrontend VITE_USER_POOL_ID
PeakLogic-Auth.UserPoolClientIdFrontend VITE_USER_POOL_CLIENT_ID
PeakLogic-Data.DbHostscripts/.env DB_HOST
PeakLogic-Data.DbSecretArnLambda env + scripts/.env
PeakLogic-Frontend.BucketNameS3 sync target
PeakLogic-Frontend.DistributionUrlPublic app URL

Step 4 — Apply the database schema

Connect to the RDS instance and run the schema SQL. The easiest method is via an EC2 instance in the same VPC or AWS Systems Manager Session Manager.

# From a bastion host or EC2 in the VPC:
psql -h YOUR_DB_HOST -U peaklogic_admin -d peaklogic \
  -f /path/to/docs/data-model.sql

The schema creates all tables, indexes, RLS policies, and the app.current_tenant_id configuration parameter.

Step 5 — Build and deploy the frontend

cd frontend
cp ../.env.example .env
# Edit .env: fill in VITE_API_URL, VITE_USER_POOL_ID, VITE_USER_POOL_CLIENT_ID

npm install
npm run build

# Deploy to S3
aws s3 sync dist/ s3://YOUR_BUCKET_NAME --delete

# Invalidate CloudFront cache
aws cloudfront create-invalidation \
  --distribution-id YOUR_DISTRIBUTION_ID \
  --paths "/*"

Step 6 — Create the first tenant record

psql -h YOUR_DB_HOST -U peaklogic_admin -d peaklogic
INSERT INTO tenants (id, name, slug, plan, status)
VALUES (gen_random_uuid(), 'Acme Corp', 'acme', 'starter', 'active')
RETURNING id;  -- copy this UUID

Step 7 — Create the first admin user

  1. Open AWS Console → Cognito → User Pools → peaklogic-users
  2. Click Create user
  3. Enter email address, set a temporary password
  4. Under Custom attributes, set custom:tenant_id to the UUID from Step 6
  5. Set custom:role to admin
  6. Click Add user to group → select admin
  7. User will be forced to change password on first login

Step 8 — Provision test devices (optional)

cd scripts
npm install
cp .env.example .env
# Edit .env with DB_HOST and DB_SECRET_ARN

# Create 5 pre-provisioned device records (no IoT Core — for testing only)
npx ts-node provision-devices.ts --count 5 --db-only

# Create real IoT Core devices (requires valid AWS credentials)
npx ts-node provision-devices.ts --count 5

Step 9 — Verify the deployment

  1. Open https://YOUR_DISTRIBUTION_URL in a browser
  2. The PeakLogic login page should appear
  3. Sign in with the admin user created in Step 7
  4. Dashboard should load (will show empty data until devices are active)
  5. Navigate to Devices → Onboard Device, enter a provisioned serial number

5. User & Tenant Management

5.1 Creating a New Tenant

A tenant is a customer organization. Creating a tenant is a two-step process: insert the DB record, then create users in Cognito and link them via custom:tenant_id.

-- 1. Insert tenant record
INSERT INTO tenants (id, name, slug, plan, status, settings)
VALUES (
  gen_random_uuid(),
  'Customer Name',
  'customer-slug',   -- lowercase, no spaces, used in URLs
  'starter',         -- starter | professional | enterprise
  'active',
  '{"webhook_url": "https://partner.example.com/webhooks/peaklogic"}'
)
RETURNING id;  -- save this UUID

-- 2. Verify it was created
SELECT id, name, slug, plan, status FROM tenants WHERE slug = 'customer-slug';

After creating the DB record, create at least one admin user in Cognito (see §5.2) with that tenant's UUID as their custom:tenant_id.

5.2 Creating User Accounts

All user creation goes through the AWS Cognito console or CLI. Self-registration is disabled.

Via AWS Console

  1. AWS Console → Cognito → User Pools → peaklogic-users
  2. Users tab → Create user
  3. Set Invitation message to send temporary password by email
  4. Enter the user's email address
  5. Under User attributes, click Add attribute:
    • custom:tenant_id → the tenant UUID from the DB
    • custom:role → one of: admin, operator, service_partner
  6. Click Create user
  7. In the Users list, click the new user → Add user to group → select matching group name

Via AWS CLI

aws cognito-idp admin-create-user \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com \
  --user-attributes \
    Name=email,Value=user@example.com \
    Name=email_verified,Value=true \
    "Name=custom:tenant_id,Value=TENANT_UUID" \
    "Name=custom:role,Value=operator" \
  --desired-delivery-mediums EMAIL

# Add user to group
aws cognito-idp admin-add-user-to-group \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com \
  --group-name operator

5.3 RBAC Roles

RoleCognito GroupPermissions
admin admin Full access: create/delete sites, assets, devices; manage users; view all data; create/delete tickets
operator operator Create/update assets and devices; acknowledge alerts; create/update tickets. Cannot delete or manage users.
service_partner service_partner View-only access to alerts and tickets assigned to them. Cannot modify data.
How roles are enforced
The Cognito JWT contains a cognito:groups claim. API Gateway validates the token; the Lambda extracts the group and calls requireRole() to gate each route. The role is also stored in custom:role for display in the UI.

5.4 Resetting a User Password

# Force password reset (user will be prompted on next login)
aws cognito-idp admin-reset-user-password \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com

# Set a specific temporary password
aws cognito-idp admin-set-user-password \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com \
  --password "TempPass123!" \
  --permanent false

5.5 Disabling / Deleting a User

# Disable (user cannot log in; data preserved)
aws cognito-idp admin-disable-user \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com

# Delete permanently
aws cognito-idp admin-delete-user \
  --user-pool-id YOUR_USER_POOL_ID \
  --username user@example.com

6. Database Administration

6.1 Connecting to RDS

The RDS instance is in an isolated subnet with no internet route. To connect as an admin, use one of the following methods:

Option A — EC2 Bastion Host (recommended for production)

# Launch a t3.nano EC2 in the VPC public subnet
# SSH into the bastion, then:
psql -h YOUR_DB_HOST -U peaklogic_admin -d peaklogic

Option B — AWS SSM Port Forwarding (no bastion needed)

# Requires SSM agent on an EC2 in the VPC
aws ssm start-session \
  --target INSTANCE_ID \
  --document-name AWS-StartPortForwardingSessionToRemoteHost \
  --parameters "host=YOUR_DB_HOST,portNumber=5432,localPortNumber=5432"

# Then in another terminal:
psql -h localhost -U peaklogic_admin -d peaklogic

Retrieving DB credentials from Secrets Manager

aws secretsmanager get-secret-value \
  --secret-id YOUR_DB_SECRET_ARN \
  --query SecretString --output text | python -m json.tool

6.3 Row-Level Security (RLS)

Every tenant-scoped table has RLS enabled. The application sets the active tenant via a PostgreSQL session variable at the start of every transaction:

BEGIN;
SET LOCAL app.current_tenant_id = 'TENANT_UUID';
-- All queries in this transaction are automatically filtered to this tenant
SELECT * FROM sites;  -- returns only this tenant's sites
COMMIT;

To query data as a specific tenant in a psql session (for debugging):

BEGIN;
SET LOCAL app.current_tenant_id = 'YOUR_TENANT_UUID';
SELECT * FROM devices WHERE status = 'online';
ROLLBACK;  -- or COMMIT if making changes

To query across all tenants (requires superuser / RLS bypass):

-- As the peaklogic_admin superuser, RLS is bypassed automatically
SELECT t.name AS tenant, count(d.id) AS device_count
FROM tenants t
LEFT JOIN devices d ON d.tenant_id = t.id
GROUP BY t.name;

6.4 Backups & Point-in-Time Restore

RDS automated backups are retained for 7 days. To restore:

# List available restore points
aws rds describe-db-instances \
  --db-instance-identifier peaklogic-db \
  --query 'DBInstances[0].LatestRestorableTime'

# Restore to a new instance at a specific point in time
aws rds restore-db-instance-to-point-in-time \
  --source-db-instance-identifier peaklogic-db \
  --target-db-instance-identifier peaklogic-db-restored \
  --restore-time 2026-06-09T03:00:00Z
After restore
A restored instance will have a different endpoint hostname. You must update the DB_HOST environment variable on the Lambda functions and redeploy, or use a Route 53 CNAME that you can update without redeploying Lambda.

7. IoT Device Management

7.1 Device Provisioning Script

Run this script before shipping devices to customers. It creates the IoT Core Thing, generates X.509 certificates, and inserts a DB record with tenant_id = NULL (unclaimed). Customers then claim devices through the onboarding wizard in the web portal.

cd scripts
npm install
cp .env.example .env
# Fill in DB_HOST and DB_SECRET_ARN (or DB_USER + DB_PASSWORD for local dev)

# Provision 10 new devices (auto-increments serial numbers)
npx ts-node provision-devices.ts --count 10

# Provision specific serial numbers
npx ts-node provision-devices.ts --serials PLG-0050,PLG-0051,PLG-0052

# DB-only mode (no AWS IoT Core calls — use for development/testing)
npx ts-node provision-devices.ts --count 5 --db-only

For each successfully provisioned device, the script creates:

FilePurpose
device-certs/{serial}/certificate.pemDevice identity certificate — flash to hardware firmware
device-certs/{serial}/private.keyPrivate key — flash to hardware, store securely, NEVER commit to git
device-certs/{serial}/device-config.jsonFirmware config: IoT endpoint, thing name, topic paths
Critical — Private Key Security
The device-certs/ directory is in .gitignore and must never be committed. If a private key is lost or compromised, the certificate must be revoked in IoT Core and a new one issued. There is no way to recover a lost private key.

7.4 Revoking a Device Certificate

Use this when a device is decommissioned, lost, or its key is suspected compromised.

# 1. Find the certificate ARN (stored in device-config.json or IoT console)
CERT_ARN="arn:aws:iot:us-east-1:ACCOUNT:cert/CERT_ID"

# 2. Deactivate the certificate (blocks MQTT connections immediately)
aws iot update-certificate \
  --certificate-id CERT_ID \
  --new-status INACTIVE

# 3. Detach from thing
aws iot detach-thing-principal \
  --thing-name plg-0001 \
  --principal $CERT_ARN

# 4. Detach policy
aws iot detach-policy \
  --policy-name PeakLogicDevicePolicy \
  --target $CERT_ARN

# 5. Delete the certificate
aws iot delete-certificate --certificate-id CERT_ID

# 6. Mark device as decommissioned in DB
UPDATE devices SET status = 'decommissioned' WHERE thing_name = 'plg-0001';

7.5 Viewing Device Activity in IoT Core

# List all registered things
aws iot list-things --thing-type-name PeakLogicSensor

# Get a specific thing's attributes
aws iot describe-thing --thing-name plg-0001

# View IoT Core ingest error log

9. Alert Rules

Alert rules are evaluated in the ingest Lambda every time a telemetry payload arrives. Rules are hardcoded per asset category in backend/ingest/handler.ts. To modify thresholds you must edit the source code and redeploy the Lambda.

Pump Rules

MetricConditionThresholdSeverityMessage
power_kw>rated_power × 1.25warningPower draw exceeds rated limit by 25%
power_kw>rated_power × 1.50criticalPower draw critically high (150% of rated)
flow_lpm<rated_flow × 0.75warningFlow rate below 75% of rated minimum
pressure_psi>rated_pressure × 1.20criticalPressure exceeds safe operating limit

Rated values come from the asset's specs JSONB column (power_kw, flow_lpm, pressure_psi). If specs are not set, defaults of 5 kW, 100 lpm, and 80 psi are used.

HVAC Rules

MetricConditionThresholdSeverityMessage
temp_c>specs.temp_max_c (default 180°C)criticalTemperature exceeds maximum operating limit
temp_c<60°CwarningTemperature below normal operating range

Alert Deduplication

Before creating a new alert, the ingest handler checks whether an open or acknowledged alert already exists for the same device, metric, and severity. If one exists, the ingest completes silently without creating a duplicate. This prevents alert storms during sustained threshold violations.

Auto-Ticket for Critical Alerts

When a CRITICAL alert is created, the ingest handler automatically:

  1. Looks up the tenant's settings.webhook_url from the tenants table
  2. Creates a service ticket with priority = emergency linked to the alert
  3. POSTs the ticket payload to the webhook URL (fire-and-forget, 8-second timeout)

Webhook Payload Format

{
  "event": "service_ticket.created",
  "ticket": {
    "id": "uuid",
    "title": "CRITICAL: Power draw critically high — pump at Main St Station",
    "priority": "emergency",
    "status": "open",
    "asset": { "name": "...", "category": "pump", "site": "..." },
    "alert": { "severity": "critical", "metric": "power_kw", "value": 9.2 },
    "created_at": "2026-06-10T14:22:00Z"
  }
}

Modifying Alert Rules

To change thresholds or add new rules:

  1. Edit backend/ingest/handler.ts — find the RULES_BY_CATEGORY constant
  2. Commit and push to the dev branch
  3. Redeploy: cd infra && npx cdk deploy PeakLogic-Api
  4. The new Lambda code takes effect within seconds of deploy completing

Authentication Flow

The frontend uses AWS Amplify v6 with the Cognito User Pool configured in frontend/src/amplify-config.ts. Authentication flow:

  1. User visits the app URL — Amplify Authenticator intercepts and shows the login form
  2. User enters email and password
  3. If first login, user is forced to set a new password
  4. Optionally, user sets up TOTP MFA (Google Authenticator)
  5. Cognito returns ID + Access tokens (stored in localStorage)
  6. App renders; tokens are refreshed automatically by Amplify before expiry
  7. Every API call injects the ID token as the Authorization header

Deploying Frontend Updates

# From project root:
cd frontend

CloudFront propagates the invalidation within ~30 seconds. Users will see the new version on their next page load.

Local Development Preview

Developers can run the frontend locally without AWS credentials using preview mode:

cd frontend
# Ensure frontend/.env.local contains:
# VITE_PREVIEW=true

npm install
npm run dev
# Open http://localhost:5173

In preview mode, the Cognito login is bypassed and the app renders with a placeholder user. API calls will fail unless a local backend is running, but all pages and UI components are visible.

Never set VITE_PREVIEW=true in production
This flag bypasses all authentication. The .env.local file is gitignored and must never be deployed to the S3 bucket or included in a production build.

13. Security Hardening

Network Security

  • RDS is in an isolated subnet with no internet gateway route — unreachable from the internet
  • Lambda can only reach RDS because the Lambda Security Group is explicitly allowed on port 5432 in the RDS Security Group
  • API Gateway is the only internet-facing entry point to the application
  • All traffic between CloudFront and S3 uses Origin Access Control — the S3 bucket URL is private

Authentication & Authorization

  • Cognito JWT tokens expire after 1 hour; refresh tokens expire after 30 days
  • All API routes require a valid JWT — there are no unauthenticated endpoints
  • Role-based access is checked in every route handler via requireRole()
  • Tenant isolation is enforced by PostgreSQL RLS — application code cannot bypass it
  • Self-registration is disabled — users can only be created by an administrator

Secrets Management

  • DB credentials are stored in AWS Secrets Manager — never in environment variables in plaintext
  • Device private keys are in device-certs/ which is gitignored — never committed to source control
  • .env and .env.local files are gitignored — never committed to source control

Production Hardening Checklist

RDS deletion protectionSet deletionProtection: true in data-stack.ts and redeploy
RDS Multi-AZSet multiAz: true in data-stack.ts and redeploy
Cognito MFAChange MFA setting from OPTIONAL to REQUIRED in auth stack

CloudTrailEnable CloudTrail in the AWS account to log all API calls

14. Troubleshooting

Frontend Issues

SymptomLikely CauseResolution
Login page shows "UserPool not configured" VITE_USER_POOL_ID or VITE_USER_POOL_CLIENT_ID is missing or wrong Check frontend/.env, rebuild and redeploy to S3
Login succeeds but app shows blank / redirects to login Cognito callback URL not configured for the CloudFront domain Add the CloudFront URL to the Cognito App Client's allowed callback URLs
API calls return 401 Token expired or VITE_API_URL is incorrect Sign out and back in; verify VITE_API_URL matches CDK output
App loads old version after deploy CloudFront cache not invalidated Run: aws cloudfront create-invalidation --distribution-id ID --paths "/*"
Page refresh returns 403 or 404 CloudFront not configured for SPA fallback Verify the FrontendStack 403/404 error response is set to /index.html

API / Lambda Issues

SymptomLikely CauseResolution
All API calls return 500 Lambda cannot connect to RDS (cold start DB error) Check CloudWatch logs for the peaklogic-api Lambda. Verify DB_HOST env var and security group rules.
API returns "Tenant ID missing from token" User's Cognito account is missing the custom:tenant_id attribute Update the user in Cognito console to add the correct tenant_id attribute
Telemetry not appearing after device sends data IoT Rule not triggering Lambda, or Lambda crashing on ingest Check /peaklogic/iot/errors log group. Check peaklogic-ingest CloudWatch logs.
Lambda timeout errors DB connection pool exhausted, or slow query Check pg_stat_activity for idle connections. Reduce pool max from 2 if running multiple Lambda instances concurrently.
Secrets Manager permission error on Lambda cold start Lambda IAM role missing Secrets Manager read permission Verify the CDK ApiStack grants the Lambda function access to the secret. Redeploy the Api stack.

Database Issues

SymptomLikely CauseResolution
Queries return empty results unexpectedly RLS is active but app.current_tenant_id is not set, or set to wrong value Always wrap queries in withTenant(). Check the tenant_id in the JWT claim.
Too many connections error Lambda pool creating too many connections (max_connections=85 on t3.micro) Reduce pool max from 2 to 1. Consider adding RDS Proxy to pool connections at the DB level.
Cannot connect to RDS from local machine RDS is in an isolated subnet — no internet route Use SSM port forwarding or a bastion host in the VPC public subnet

IoT Device Issues

SymptomLikely CauseResolution
Device cannot connect (MQTT auth error) Certificate not active, wrong IoT endpoint, or private key mismatch Verify certificate status in IoT Core console. Check device-config.json endpoint matches your region.
Device connects but telemetry not appearing in DB IoT Rule disabled, thingName in payload doesn't match the registered thing name, or ingest Lambda error Check IoT Rule status. Verify payload includes thingName field. Check /peaklogic/iot/errors.
Device serial not found during onboarding Device was not provisioned, or serial was entered incorrectly Check devices table: SELECT * FROM devices WHERE serial ILIKE '%PLG-XXXX%';
Device shows as already claimed tenant_id is not NULL in the devices table Check which tenant claimed it: SELECT tenant_id, status FROM devices WHERE serial='PLG-XXXX';

Restoring the Database from a Snapshot

# List available snapshots
aws rds describe-db-snapshots \
  --db-instance-identifier peaklogic-db \
  --query 'DBSnapshots[*].{ID:DBSnapshotIdentifier,Time:SnapshotCreateTime}'

aws rds restore-db-instance-from-db-snapshot \

  --db-snapshot-identifier YOUR_SNAPSHOT_ID \

  --environment "Variables={DB_HOST=NEW_HOST,DB_NAME=peaklogic,...}"

Full Stack Redeploy (from scratch)

If all CDK stacks need to be redeployed (e.g., after accidental deletion):

  1. Run cd infra && npx cdk deploy --all
  2. Restore DB from snapshot if data needs to be preserved (see above)
  3. Update frontend .env with new CDK output values
  4. Rebuild and sync frontend: npm run build && aws s3 sync dist/ s3://BUCKET
  5. Invalidate CloudFront cache
  6. Verify Cognito users still exist (User Pool is preserved in CDK RETAIN policy)

Backing Up Device Certificates

Device private keys cannot be re-downloaded from AWS after initial provisioning. Ensure the device-certs/ directory is backed up securely (encrypted storage, not git):

# Create an encrypted zip of all device certificates
# Store this in a secure, access-controlled location (not git)
Compress-Archive -Path "device-certs" -DestinationPath "device-certs-backup-$(Get-Date -Format 'yyyyMMdd').zip"
Note on Device Certificate Loss
If a private key backup is lost, you must revoke the affected certificate(s) in IoT Core and re-provision the devices. The physical hardware will need to be reflashed with the new certificates. This is why secure off-git backup of device-certs is critical.
