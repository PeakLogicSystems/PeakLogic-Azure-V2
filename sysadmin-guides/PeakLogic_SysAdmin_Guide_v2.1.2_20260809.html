1. System Overview

Where PeakLogic is heading — the unified platform (2026)

PeakLogic is being reframed from a single-tier monitoring SaaS into a unified industrial operations platform that sits above existing SCADA/control systems — it never replaces safety-rated PLC control logic. Three components form one product, plus a first-class help system:

  • PeakLogicSystems — the core cloud intelligence layer (this platform): multi-tenant monitoring, AI anomaly detection, predictive maintenance, compliance automation, technician/CMMS workflows, enterprise reporting.
  • PeakView360 — the modernized HMI/SCADA operator experience: real-time screens, alarm management, equipment dashboards, historian.
  • PeakLogic Hubs — on-prem edge units: PLC/RTU acquisition, edge processing, offline reliability, outbound-only cloud sync — a productization of the existing PeakLogic Edge (windows-hub/).
  • PeakAssist — a first-class, offline-capable, contextual help system.

Administrator reality check: the cloud schema for Hubs, HMI screens/tags, CMMS work orders/PM, compliance reports, and PeakAssist content ships as migrations (1784142000000–…240000), and self-contained backend logic (PM-work-order generation, compliance-report generation, PeakAssist resolution) is built and unit-tested. But PeakView360, the Hubs' PLC drivers, and PeakAssist delivery/sync are design-stage — not deployed. The operations detailed in the rest of this guide remain the current reality; full admin procedures for each new component will be added as it ships. Canonical naming and the full plan: docs/architecture/unified-platform-integration-plan.md.

PeakLogic is a multi-tenant, cloud-native IoT SaaS platform that monitors industrial and commercial equipment — pumping stations, HVAC systems, pool equipment, and QSR (quick-service restaurant) assets — in real time. Sensors attached to physical equipment transmit telemetry data to Azure IoT Hub over MQTT/TLS. The platform evaluates that data against threshold rules, raises alerts, and automatically creates service tickets for partner companies when critical thresholds are breached.

As of v1.1.0, the platform also supports a second, separate user population: channel partners — pool-service companies (e.g. a Pinch-A-Penny franchise) who install PeakLogic sensors at their own customers' sites and log into a white-label, branded portal to draw technician territories, dispatch daily routes, and see real-time chemistry/status data across every customer site attributed to them. This is a genuinely separate identity and access surface from the tenant-side application described throughout most of this guide — see §5.5 and §8.2.

Business Purpose

  • Detect abnormal equipment behavior before failure occurs
  • Reduce risk of equipment damage and property loss for customers
  • Proactively trigger service tickets to partner service companies via webhook
  • Give channel partners real, continuously-measured evidence (chemistry, status) to justify service visits, replacing manual field checks

Multi-Tenancy Model

PeakLogic uses a hybrid pooled model: all tenants share a single PostgreSQL database, but every tenant-scoped table carries a tenant_id column and PostgreSQL Row-Level Security (RLS) policies enforce data isolation at the database level. No application query can accidentally cross tenant boundaries because the database engine enforces it.

v1.1.0 — RLS is now actually enforced against the app's own DB role
Prior to v1.1.0, the application connected to PostgreSQL as peaklogic_admin — the same role that owns every table. PostgreSQL table owners silently bypass RLS by default unless FORCE ROW LEVEL SECURITY is explicitly set, which no table in this schema ever had. This meant every "RLS enforces isolation" claim in this platform's history, back to the very first migration, described a mechanism that would not have actually worked once deployed. It was never live-exploited (nothing had been deployed to a real Azure subscription before this was found), but it is the single most important fact in this release. See §6.3 for full detail.

Channel-partner access is a second, deliberately different scoping dimension layered on top of the tenant model above: a channel-partner session can read across every tenant attributed to it (via tenants.channel_partner_id), and a technician's session is further restricted to the sites within their own assigned territory. This is enforced the same way tenant isolation is — real PostgreSQL RLS policies, not application-level filtering — see §6.3.

3.2 Cost kill switch

Azure Cost Management budgets are alert-only — there is no native equivalent of Azure Budget Actions. PeakLogic therefore ships its own, graduated across four thresholds:

  • 50% / 80% — email only, every stage, via monitoring.bicep's existing on-call Action Group.
  • 90% (dev/staging only) — email and sets a cost-throttle-active Key Vault flag for budget-conscious background workloads to check and skip themselves. Stops nothing by itself.
  • 100% (dev/staging only) — a dedicated peaklogic-{stage}-cost-killswitch-ag Action Group emails and invokes a standalone Function (ops/cost-killswitch/) that stops the Postgres server.
  • The kill-switch Function is deliberately separate from the main app so the "can stop the database" permission stays on a narrowly-scoped identity.
  • Auth is a self-managed shared secret (?secret=, constant-time comparison, fails closed if unset) rather than a Function host key.
Prod does not deploy the 90%/100% automated actions (changed 2026-08-09)
An unattended mechanism able to stop the production database is itself an availability risk on the one environment where that risk is least acceptable. Prod's 90% and 100% budget notifications route to the same on-call email group as 50%/80% — no Function App, no Postgres-stop role assignment, and no automated throttle flag exist for the prod stage at all. If prod's spend needs to be capped, that is a manual on-call response to the email alert, not an automated action. Dev and staging keep the full graduated shape described above.
A stopped Postgres server auto-restarts after 7 days
This is an Azure platform rule, independent of what stopped it. The kill switch buys time to fix the cost driver; it is not a permanent shutdown. (Applies to dev/staging only — see above.)

Every infra-azure deploy requires alertEmail and killswitchSecret for all three stages, including prod — both have no default and fail the deployment loudly if omitted. For prod specifically, killswitchSecret is accepted but inert: no deployed resource references it.

    az group create --name peaklogic-dev-rg --location <region>
  2. Deploy the Entra app registrations — three separate deployments against three different tenants, each at subscription scope: 
    az login --tenant <tenant-id>

    Repeat for partners.bicep and staff.bicep. See infra-azure/entra/README.md for the output-to-parameter mapping.
  3. Generate the two management client secrets by hand. Client secrets are not declarative in Bicep for app registrations — one az ad app credential reset per management app, stored in Key Vault.
  4. Deploy the main template: 
    az deployment group create \
  --resource-group peaklogic-dev-rg \
  --template-file infra-azure/main.bicep \
  --parameters stage=dev \
  --parameters alertEmail=you@example.com \
  --parameters dbAdminPassword=<secret> \
  --parameters killswitchSecret=$(openssl rand -hex 32)
  5. Run database migrations — see §6.
  6. Deploy backend code — the Bicep deploy provisions the Function App but never publishes application code. CI does this as a separate step (Azure/functions-action).

5. User & Tenant Management

5.1 Three separate identity surfaces

PeakLogic does not have one user directory. Identity is split across three isolated Microsoft Entra tenants, which is the strongest boundary Entra offers:

SurfaceEntra tenantWhoRole source
CustomersPeakLogicCustomers (External ID / CIAM)Tenant admins and operators at customer facilitiesApp Roles: admin, operator
PartnersPeakLogicPartners (External ID / CIAM)Channel-partner staff (service providers)Database — channel_partner_users.role, resolved per request
StaffPeakLogic corporate workforce tenantPeakLogic's own employeesApp Roles: superadmin, account_manager
Why partners resolve roles from the database, not a token claim
An ordinary partner user's role is data about the relationship, not a directory fact — it changes as territory and account assignments change. Only channel_partner_manager exists as an App Role there, used purely as an identity-type discriminator.

5.2 How a request is authorized

  1. The caller presents a bearer token. backend/shared/auth.ts validates it offline — RS256 signature against the surface's JWKS endpoint, plus issuer and audience.
  2. Tenant identity comes from a custom-attribute claim (extension_*); role comes from the roles claim (customers/staff).
  3. Every check fails closed. Missing token, missing tenant claim, or no role assigned all reject — there is no silent default role.
  4. The route opens a transaction via withTenant() / withChannelPartner() / withStaffSession(), which sets the RLS session variable and checks suspension status before running anything.

The database columns storing the directory subject are still named cognito_sub — a legacy name retained deliberately to avoid a schema migration with no functional benefit. They hold the Entra oid (the stable directory object id), not a pairwise sub.

5.3 Provisioning users

All user creation is admin-invited; there is no self-service signup on any surface. backend/shared/identity.ts creates the directory user via Microsoft Graph and assigns the App Role where applicable, then the route inserts the database row.

OperationEndpoint
Tenant admin adds a team memberPOST /v1/settings/team
Partner admin adds a partner userPOST /v1/partner/users
Staff creates a tenantPOST /v1/admin/tenants
Staff creates a staff userPOST /v1/admin/staff-users

Directory and database writes are not transactional together
The Graph call and the database insert are two systems. A failure between them can leave a directory user with no database row (or the reverse) — it must be reconciled by hand. This is a known, accepted limitation.

5.4 Tenant suspension

Setting tenants.status = 'suspended' blocks the human-facing API for that tenant immediately — the check lives inside withTenant(), so every tenant-scoped route inherits it. Telemetry ingestion is deliberately unaffected: a suspended tenant's devices keep reporting rather than losing data. There is no self-service suspension workflow; it is a manual operation.

5.5 Password and MFA

Entra manages these through its own self-service flows, not a backend API. GET /v1/settings/mfa and PUT /v1/settings/password return the self-service deep link for the client to send the user to — they do not perform the action.

MFA is not enforced
MFA enforcement and Conditional Access policy are not configured. Neither is an app-registration resource, so neither is covered by the Bicep templates — both remain open items.

6.3 Row-Level Security (RLS) — including the FORCE RLS fix

Read this box before touching RLS on this platform
The v1.0.0 version of this guide said "as the peaklogic_admin superuser, RLS is bypassed automatically" — that framing was wrong, and describes exactly the bug this release fixed. peaklogic_admin is not a real PostgreSQL superuser (PostgreSQL Flexible Server never grants that on the master user) — it appeared to bypass RLS for a completely different reason: it owns every table (it's also the role every migration runs as), and PostgreSQL table owners silently bypass RLS by default, independent of superuser status, unless FORCE ROW LEVEL SECURITY is explicitly set on the table. No table in this schema had that set before v1.1.0. This means every "RLS enforces isolation" claim in this platform's history — including the very tenant isolation this section exists to document — described a mechanism that would not have actually held once deployed against a real database, since the app connects as this same table-owning role. It was never live-exploited (nothing had been deployed to a real Azure subscription when this was found), but it would have been on the very first real deploy. Fixed in migration 1783728060000_force-row-level-security.sql — every RLS-enabled table now also has FORCE ROW LEVEL SECURITY, and this guide's examples below reflect the corrected, actually-enforced behavior.

Every tenant-scoped table has RLS enabled and forced. The application sets the active tenant via a PostgreSQL session variable at the start of every transaction:

BEGIN;
SET LOCAL app.current_tenant_id = 'TENANT_UUID';
-- All queries in this transaction are automatically filtered to this tenant
SELECT * FROM sites;  -- returns only this tenant's sites
COMMIT;

To query data as a specific tenant in a psql session (for debugging) — this now genuinely enforces isolation, including for peaklogic_admin:

BEGIN;
SET LOCAL app.current_tenant_id = 'YOUR_TENANT_UUID';
SELECT * FROM devices WHERE status = 'online';
ROLLBACK;  -- or COMMIT if making changes

Channel-partner sessions use a different set of variables — added v1.1.0

A channel-partner request never sets app.current_tenant_id at all. Instead:

BEGIN;
SET LOCAL app.current_channel_partner_id = 'PARTNER_UUID';
SET LOCAL app.current_channel_partner_user_id = 'CHANNEL_PARTNER_USER_UUID';
SET LOCAL app.current_channel_partner_role = 'technician';  -- or 'partner_admin'
-- A partner_admin sees every route under their partner;
-- a technician sees only their own day's route.
SELECT * FROM route_assignments;
COMMIT;

Every pre-existing tenant_isolation policy uses current_setting(..., true) (the missing_ok form) rather than erroring when app.current_tenant_id is unset — a real, deliberate fix, since a channel-partner session never sets it, and the original policies would have thrown an error rather than simply denying access, before the new cross-tenant policies ever got evaluated.

Staff sessions use a third, different set of variables — added v1.2.0

A staff session resolves its own identity in two stages, in a specific order that matters (see the box below):

BEGIN;
-- Stage 1: set directly from the JWT, before any row has been looked up
SET LOCAL app.current_staff_cognito_sub = 'SUB_FROM_JWT';
SET LOCAL app.current_staff_role = 'account_manager';  -- or 'superadmin', from the token's roles claim

-- Stage 2: only once peaklogic_staff_users has been queried by cognito_sub
-- (permitted by the policy below) and its id resolved:
SET LOCAL app.current_staff_user_id = 'RESOLVED_STAFF_USER_UUID';

-- For "acting on a tenant" endpoints only, and only after verifying an
-- account_assignments row (or role = superadmin, which skips that check):
SET LOCAL app.current_tenant_id = 'TARGET_TENANT_UUID';
COMMIT;
Why cognito_sub, not id, is the first variable set
peaklogic_staff_users' own RLS policy permits a session to see its own row by matching cognito_sub = current_setting('app.current_staff_cognito_sub', true) — deliberately not keyed on id, because id is exactly the value this lookup exists to discover. A staff session only learns its own id after this lookup succeeds, so the policy has to be satisfiable using only what's already known pre-lookup (cognito_sub, straight off the JWT). This was a real bug in the first draft of this policy, caught and fixed before any code shipped — see §5.7's info box and Database Schema §4.5 for the full writeup.

Querying across all tenants for legitimate ops/reporting purposes

No dedicated reporting/bypass role exists yet
There is currently no non-owning, RLS-bypassing application role built for this platform (a real, flagged-but-not-implemented option — Multi-Tenant Architecture §6 item 6, tracked as TD-7 in the Technical Debt Register). Azure PostgreSQL Flexible Server also blocks granting the BYPASSRLS attribute outright. The only way to run a genuine cross-tenant query today is to temporarily disable forcing on the specific table, as peaklogic_admin (which owns every table and therefore has this privilege), then restore it immediately: 
-- Temporarily disable, run the cross-tenant query, then RE-ENABLE immediately.
-- Never leave a table in this state.
ALTER TABLE devices NO FORCE ROW LEVEL SECURITY;

SELECT t.name AS tenant, count(d.id) AS device_count
FROM tenants t
LEFT JOIN devices d ON d.tenant_id = t.id
GROUP BY t.name;

ALTER TABLE devices FORCE ROW LEVEL SECURITY;  -- do not skip this step

Treat this as a rare, deliberate, logged administrative action — not a routine query pattern. If cross-tenant reporting becomes a frequent need, that's a real argument for finally building the dedicated non-owning reporting role (TD-7).

Device-claim and provisioning sessions — added v1.1.0

A device before it's claimed by a customer has tenant_id = NULL. Reading/writing it (during claim, or during scripts/provision-devices.ts) requires its own dedicated session markers, since neither app.current_tenant_id nor a channel-partner marker applies:

-- Device claim flow sets:
SET LOCAL app.claim_context = 'true';
-- Provisioning script sets (plain SET, not SET LOCAL — the script isn't
-- wrapped in one single transaction for its whole run):
SET app.provisioning_context = 'true';

These are intentionally narrow — each only grants the one specific lookup it's needed for (an unclaimed device by serial), not general device visibility. An earlier draft of this fix briefly leaked every unclaimed device system-wide to any tenant's normal device list before being caught in review; the shipped version does not have this problem, but it's a useful example of how easy this class of bug is to introduce when adding a new RLS policy — always ask both "does this still work for every legitimate caller" and "could this grant more than intended to some other caller running the same query."

7. IoT Device Management

7.1 Identity model

Every device and every PeakLogic Hub authenticates with its own X.509 certificate — there are no shared secrets, API keys, or device passwords anywhere in the design. Certificates are issued per unit and enrolled individually in the Device Provisioning Service (DPS); the IoT Hub device identity is the device serial.

Outbound-only, by design
Devices and Hubs open an outbound MQTT/TLS session to IoT Hub. No inbound port, port-forward, firewall exception, or VLAN is ever required on a customer network. This is what makes the platform deployable inside enterprise and zero-trust environments.

7.2 What Bicep does and does not do

  • iot.bicep provisions the IoT Hub, the DPS instance, and the link between them.
  • It deliberately creates no enrolment entries — individual X.509 enrolment is a per-device runtime operation, not template state.
  • Two scoped authorization policies exist instead of using the all-powerful default iothubowner for everything: ingestConnect (ServiceConnect only, for the ingest Function) and registryReadWrite (for the admin-plane revocation path).

7.3 Decommissioning a device

DELETE /v1/devices/{deviceId} sets the database status to decommissioned and calls disableDeviceIdentity() (backend/shared/device-identity.ts) to disable the IoT Hub device identity, so a revoked unit cannot reconnect. The call is best-effort and never blocks the database operation.

Revocation is inert until DPS enrolment ships
No code path yet creates real IoT Hub device identities, so disableDeviceIdentity() currently no-ops safely. It becomes effective the moment DPS enrolment is built.
Not yet verified against a live Azure deployment
No device has ever been provisioned against a real IoT Hub or DPS instance. The enrolment scripts themselves are not written.

Alert Deduplication

Before creating a new alert, the ingest handler checks whether an open or acknowledged alert already exists for the same device, metric, and severity. If one exists, the ingest completes silently without creating a duplicate. This prevents alert storms during sustained threshold violations.

Auto-Ticket for Critical Alerts

When a CRITICAL alert is created, the ingest handler automatically:

  1. Looks up the tenant's settings.webhook_url from the tenants table
  2. Creates a service ticket with priority = emergency linked to the alert
  3. POSTs the ticket payload to the webhook URL via backend/shared/webhook.ts's postWebhook() (fire-and-forget, 8-second timeout)
v1.1.0 — Critical SSRF fix, live and exploitable in v1.0.0
POST /v1/tickets previously accepted an arbitrary webhookUrl directly from the request body with zero validation — any authenticated operator+ user could make this Function send an outbound request anywhere they chose, including internal network reconnaissance. The same unguarded pattern existed a second time in this exact auto-webhook code path. Fixed with a shared, tested postWebhook() function: HTTPS-only, resolves the hostname, and rejects private/loopback/link-local address ranges (including 169.254.0.0/16, which covers EC2's IMDS, ECS/Fargate's task-metadata endpoint, and Function's own AZ-metadata endpoint). Disclosed residual gap: validates at check-time, not connection-time, so DNS rebinding isn't fully closed — tracked as TD-2 in the Technical Debt Register (§16), judged disproportionate to fully solve at MVP scale.

Modifying Alert Rules

To change thresholds or add new rules:

  1. Edit backend/ingest/rules.ts — find the RULES_BY_CATEGORY constant
  2. Add or update tests in backend/ingest/rules.test.ts (28 tests exist as of v1.1.0 — a real, run-and-verified suite, not just written)
  3. Commit and push to the dev branch (CI runs typecheck + tests automatically, §2.8)
  4. Redeploy: cd infra && npm run deploy:dev (or the equivalent for the target stage — the stage flag is required, §4)

13.2 Tenant isolation

Every tenant-scoped query runs through withTenant() (or the channel-partner / staff equivalents) in backend/shared/db.ts, which opens a transaction and sets the RLS session variable via SELECT set_config('app.current_tenant_id', $1, true).

Do not use SET LOCAL with a bind parameter
SET LOCAL x = $1 is not valid PostgreSQL — SET is a utility command that does not accept query parameters. Every isolation primitive used this broken form until 2026-08-01 and therefore had never executed successfully against a real database. Always use set_config(name, value, true).

Table owners bypass RLS unless FORCE ROW LEVEL SECURITY is set — it is, on every tenant-scoped table. Note that superusers bypass RLS unconditionally, which is why integration tests connect as a dedicated non-superuser role.

13.3 Session revocation

POST /v1/settings/team/{userId}/revoke-sessions calls Microsoft Graph's revokeSignInSessions. This invalidates refresh tokens and browser sessions but does not retroactively invalidate an already-issued access token still inside its expiry window — the backend validates JWTs offline with no Continuous Access Evaluation.

15. Disaster Recovery

Never drilled
Nothing has been deployed, so no backup has ever been taken and no restore has ever been performed. Every procedure here is a documented starting point, not a tested runbook.

15.1 What protects the data

InfrastructureFully reproducible from Bicep in source control
Application codeRedeployable from any tagged commit

15.2 Recovery paths

  1. Data corruption / bad migration — point-in-time restore to a new server, verify, then repoint postgres-admin-credential in Key Vault.
  2. Bad infrastructure change — check out the previous release tag and re-run az deployment group create.
  3. Bad application code — re-run the deploy workflow against a previous tag (deploy-prod.yml accepts a ref input for exactly this).
  4. Total resource-group loss — recreate the group, redeploy Bicep, restore the database, republish code, re-enrol devices.

15.3 Honest limits

  • No geo-redundancy. A full region loss is not currently recoverable within the backup configuration.
  • RPO/RTO targets are unvalidated. No restore has been timed.
  • Device re-enrolment is unwritten. DPS enrolment scripting does not exist, so the device-plane recovery step above is currently theoretical.
